# mokano.live 팬 편지 작성 기능 — 개발 에이전트용 프롬프트

---

너는 기존 mokano.live 프로젝트에 기능을 추가하는 개발자다. 현재 저장소 구조를 먼저 확인한 후, 팬이 모카에게 마지막 무대 기념 편지를 보내는 기능을 실제 동작하도록 구현하라. 계획만 제시하지 말고 코드, Supabase 마이그레이션, 필요한 문서와 검증까지 완료하라.

## 0. 참고사항
D:\Projects\CodingLan\Mokano-2026-Graduation-Countdown 의 모든 내용을 읽고 시작하라. 이 페이지와 거의 같은 CSS 와 이모지를 사용하라.

## 1. 작업 범위와 기존 프로젝트 확인

- 기존 프레임워크, 라우터, 패키지 매니저, Supabase 연결 방식, 서버 실행 환경, 관리자 권한 구조, 마이그레이션 규칙을 확인하고 그대로 따른다. Next.js라고 임의로 단정하거나 새 프로젝트로 교체하지 않는다.
- 기존 mokano.live와 같은 Supabase 프로젝트를 사용한다. 환경변수 이름은 기존 것을 우선 사용하며 값을 출력하거나 문서에 기록하지 않는다.
- 신규 팬 페이지 경로는 `/letters/write`를 기본으로 하되 기존 라우팅 규칙에 맞춘다. 기존 메뉴에 ‘모카에게 편지 쓰기’ 링크를 자연스럽게 추가한다.
- 이번 구현 범위는 팬 작성 페이지, 저장 API, Supabase 테이블, 48시간 재작성 제한, 배경 애니메이션이다.
- 관리자 검수 화면과 모카 전용 열람 화면은 이번에 새로 만들지 않는다. 이후 연결할 수 있도록 검수 상태와 최초 읽음 시각을 데이터에 준비한다.
- 기존 카운트다운·팬 메시지·관리자 기능을 유지하고 전역 CSS 충돌을 피한다. 관련 없는 리팩터링과 의존성 업그레이드는 하지 않는다.

## 2. 디자인: 전달된 팬 작성 시안 + 카운트다운 ZIP

팬 작성 시안의 구도를 참고하고 ZIP의 `style.css`, `script.js`, `index.html`에서 배색과 이모지 동작을 확인한다. 자료가 없으면 아래 명세로 진행한다. 

기본 디자인 토큰:

```css
--letter-bg-1: #EEF1F8;
--letter-bg-2: #DDD9ED;
--letter-bg-3: #F3E3EB;
--letter-text: #34354A;
--letter-text-sub: #686A80;
--letter-accent: #77649C;
--letter-pink: #C58EA5;
--letter-warm: #E8D5AD;
--letter-paper: #FFFDF8;
--letter-card-bg: rgba(255, 255, 255, 0.58);
--letter-card-border: rgba(255, 255, 255, 0.78);
```

- 배경: `linear-gradient(165deg, #EEF1F8 0%, #DDD9ED 52%, #F3E3EB 100%)`.
- 중앙의 은은한 흰색 광원과 위에서 내려오는 옅은 따뜻한 무대 조명을 겹친다.
- 카드: 반투명 흰색, 28px 모서리, 12px 배경 흐림, 부드러운 보라색 그림자. backdrop-filter 미지원 시 충분히 불투명한 배경으로 대체한다.
- 입력창은 18px 내외 모서리, 기본 버튼은 pill 형태. 주요 버튼은 `#77649C → #8E7AB4` 그라데이션과 흰색 글씨.
- 기존 폰트를 우선 사용하고 Pretendard 계열의 단정한 한글 산세리프를 적용한다. 과도한 손글씨·꽃·사진 장식은 추가하지 않는다.
- 편지지에는 아주 옅은 가로줄을 사용하되 입력 글자의 행간과 맞춘다. 스크롤과 줄바꿈이 자연스럽게 동작해야 한다.
- 모바일 우선 단일 열, 모바일 좌우 여백 16px, 데스크톱 최대 너비 약 560~640px. 작은 화면에서 입력창 확대나 가로 스크롤이 발생하지 않도록 한다.
- 봉투 장식은 라벤더 봉투와 핑크 하트 봉인으로 표현한다. 기존 CSS 도형 또는 가벼운 SVG로 충분하며 이미지 생성 API는 필요 없다.

화면 구성과 문구:

1. 상단: 기존 홈/마지막 무대 페이지로 돌아가는 링크. 실제 존재하는 경로를 연결한다.
2. 작은 라벨: `MOKA · LAST STAGE`.
3. 제목: `모카에게 보내는 편지`.
4. 부제: `함께한 마음을, 오래 남을 편지로.`
5. 설명: `아쉬운 마음도, 앞으로의 응원도 괜찮아요.`
6. 편지 카드: `TO. MOKA`, 보내는 사람, 편지 내용, 분량 안내, 전송 버튼.
7. 안내 카드: `마음을 전하기 전에`.
8. 하단: `움직임 끄기/켜기`, 기존 사이트 푸터와 어울리는 `모카 한 모금 / 함께한 시간은 오래 남아.`

## 3. 팬 입력 및 전송 UX

- 로그인 없이 작성할 수 있다.
- 이름/닉네임은 선택 입력이다. 앞뒤 공백을 제거한 결과가 비어 있으면 DB에는 null로 저장하고 표시할 때 ‘익명’으로 처리한다. 이름은 최대 40자로 제한한다.
- 편지 내용은 필수 plain text다. 한글, 일본어, 이모지, 개행을 보존한다. HTML 또는 Markdown 실행·렌더링을 하지 않는다.
- 기존 요청은 **2,000자 아닌 최대 2,000줄**이다. 실제 개행 기준으로 계산하고, 화면 폭에 따른 자동 줄바꿈은 줄 수에 포함하지 않는다. CRLF/CR을 LF로 정규화한다.
- 공백뿐인 편지는 차단한다. 긴 단일 행을 포함한 과도한 요청 방지를 위해 본문 UTF-8 256KiB 상한도 둔다. 두 제한을 모두 안내하고 클라이언트·서버에서 동일하게 검사한다. 2,000줄을 2,000자로 바꾸지 않는다.
- 큰 내용을 입력해도 별도의 DOM 행 수천 개를 만들지 않고 일반 textarea로 처리한다. 현재 줄 수를 표시한다.
- 이름 안내: `비워 두면 익명으로 전달돼요.`
- 입력 가이드: `추억 한 장면이나 고마웠던 마음을 적어 주세요.`
- 전달 안내: `편지는 관리자 확인 후 모카에게 전달돼요.`
- 전송 안내: `편지는 한 번 보내면 48시간 후에 다시 보낼 수 있어요.`
- 전송 버튼은 `편지 보내기`, 요청 중에는 `편지 보내는 중…`으로 바뀌고 중복 클릭을 막는다.
- 성공: `편지를 잘 받았어요. 관리자 확인 후 모카에게 전달할게요.`와 다음 작성 가능 시각을 표시한다.
- 실패하면 작성 내용과 이름을 유지하고 원인에 맞는 재시도 안내를 제공한다. DB 저장 전에 성공 화면을 표시하지 않는다.
- 편지 원문은 기본적으로 localStorage에 저장하지 않는다. 새로고침 후 복구 기능은 이번 범위에 넣지 않는다.
- 입력 라벨, 키보드 탐색, 명확한 focus, 오류 연결, 적절한 aria-live를 제공한다. 카운트다운을 매초 스크린리더로 읽지 않는다.

## 4. Supabase 테이블과 접근 권한

기존 테이블과 충돌하지 않는 새 이름으로 마이그레이션을 작성한다. 아래 이름을 기본으로 하되 충돌 시 이유를 기록하고 다른 이름을 선택한다. 기존 테이블을 DROP하거나 다른 용도로 바꾸지 않는다.

`moka_graduation_letters`:

| 컬럼 | 용도 |
| --- | --- |
| id | UUID 기본 키 |
| sender_name | nullable text, 비어 있으면 익명 |
| content | 필수 text, 편지 원문 |
| moderation_status | pending / approved / hidden, 기본 pending |
| created_at | DB에서 설정한 timestamptz |
| reviewed_at | nullable timestamptz, 향후 검수용 |
| read_at | nullable timestamptz, 향후 모카의 최초 열람 시각 |

이와 별도로 서버만 접근 가능한 제출 제한용 테이블을 둔다. 브라우저 식별자 해시, 마지막 성공 시각, 다음 제출 가능 시각, 중복 요청 처리에 필요한 정보를 저장한다. 식별자 해시 등 운영 메타데이터가 향후 편지 열람 응답에 포함되지 않도록 분리한다.

- RLS를 활성화하고 anon 및 일반 authenticated 역할의 편지 직접 SELECT/INSERT/UPDATE/DELETE 권한을 차단한다. ‘로그인 사용자면 모두 관리자’로 처리하지 않는다.
- 편지 저장은 기존 서버 API 또는 Supabase Edge Function을 통해 수행한다. 기존 서버 환경이 있으면 우선 재사용한다.
- 서버 측 service role/secret은 서버에서만 사용하고 public 환경변수·브라우저 번들·로그에 노출하지 않는다.
- 저장 서버는 허용한 이름·내용만 입력으로 받고, 검수 상태·생성 시각·읽음 상태는 클라이언트가 지정할 수 없게 한다.
- 최초 저장은 반드시 pending이며, 성공 응답은 접수 성공·다음 작성 가능 시각 등 필요한 최소 정보만 제공한다. 팬 대상 편지 전체 목록 API는 만들지 않는다.
- 관리자 권한 정책이 필요하면 기존 실제 권한 판단 방식을 재사용한다. 확인되지 않은 profiles 컬럼이나 관리자 역할을 임의로 가정하지 않는다.
- 필수 데이터 제약과 조회에 필요한 인덱스를 정의한다. RPC를 사용한다면 PUBLIC/anon/authenticated 실행 권한을 명시적으로 제한하고, SECURITY DEFINER 사용 시 안전한 search_path와 객체 경로를 적용한다.
- 로컬 마이그레이션과 적용 절차를 제공한다. 연결 권한이 없으면 실행 가능한 SQL까지 완성하고 원격 DB에 적용된 것처럼 보고하지 않는다.

## 5. 48시간 재작성 제한과 중복 저장 방지

성공한 제출의 DB 시각부터 정확히 48시간이 지나면 같은 브라우저에서 다시 작성할 수 있도록 한다. 자정 초기화 방식은 사용하지 않는다.

브라우저:

- 서버가 발급한 충분히 긴 무작위 브라우저 식별자를 HttpOnly 쿠키에 저장한다. 운영 HTTPS에서는 Secure, SameSite=Lax, 적절한 Path를 설정한다. 쿠키 수명은 제한 기간보다 길게 둔다.
- 클라이언트가 임의로 지정한 식별자를 그대로 신뢰하지 않는다. 서버 서명 또는 서버 발급 내역 검증을 사용한다.
- localStorage에는 `mokano:letters:nextAllowedAt` 같은 이름으로 서버가 반환한 다음 작성 가능 시각만 캐시한다. 이것은 UI 복원용이며 제한의 최종 판단 근거가 아니다.
- 페이지를 열면 서버의 작성 가능 상태를 조회한다. 제한 중에는 입력 폼 대신 친절한 안내와 남은 시간을 보여준다. 서버 시각 기준으로 보정하고 화면 재활성화·제출 시 재확인한다.
- 여러 탭은 storage 이벤트 등으로 상태를 동기화한다. 저장소 접근이 차단되면 예외로 페이지가 깨지지 않게 하고 서버 상태를 사용한다. 식별 쿠키를 유지할 수 없으면 제한 없는 전송으로 우회하지 말고 안내한다.

서버/DB:

- 식별자에 대한 제출 제한과 편지 저장을 **하나의 DB 트랜잭션에서 원자적으로** 처리한다. 최초 동시 요청에도 한 건만 저장되도록 고유 키와 잠금/조건부 갱신을 조합한다.
- 단순히 SELECT로 시간을 확인하고 별도 INSERT하는 방식은 사용하지 않는다.
- 제한 중에는 HTTP 429와 서버가 계산한 nextAllowedAt, 적절한 Retry-After를 반환한다. 실제 남은 시간 이상으로 제한을 연장하지 않는다.
- 같은 제출 요청을 재시도할 때는 동일한 idempotency key를 사용한다. 응답 유실 후 재시도해도 편지가 중복 저장되지 않고 기존 성공을 확인할 수 있어야 한다. 키는 서버의 브라우저 식별자와 연결해 검증한다.
- 실패·유효성 오류·DB 롤백은 48시간 제한을 시작하지 않는다. 검수 상태 변경이나 편지 삭제가 제출 제한 기록을 초기화하지 않도록 한다.
- 요청 본문 크기를 파싱 전에 제한하고, same-origin 검증과 기존 CSRF 방어를 적용한다. 외부 Edge Function이면 허용 Origin을 명시한다. CORS만을 인증 수단으로 간주하지 않는다.
- 무차별 요청에 대한 짧은 구간의 추가 요청 제한은 기존 인프라가 있으면 재사용한다. IP 하나를 48시간 차단해 같은 네트워크의 다른 팬까지 막지 않는다.
- 쿠키 삭제·시크릿 창·다른 기기에서는 새로운 브라우저로 보일 수 있다. 본 기능을 ‘동일인 48시간 완전 차단’으로 표현하지 않는다. 로그인이나 기기 지문 수집을 임의로 추가하지 말고, 이 한계를 문서에 기록한다.

## 6. ZIP과 같은 다양한 이모지 애니메이션

- ZIP의 emoji layer와 fall/sway/rise/glow 동작을 읽고 기존 프레임워크에 맞게 분리해서 재사용한다. 기존 DOM을 직접 조작하는 스크립트를 React 등에 그대로 중복 삽입하지 않는다.
- 장식 비율은 아쉬움·눈물 계열 약 70%, 응원·희망 계열 약 30%다. 예: 🥹 😢 🥲 😭 / 💜 ✨ 🫶 🌷.
- 네 가지 동작을 모두 구현한다: 천천히 내려오기, 좌우 흔들림과 작은 회전, 부드럽게 위로 떠오르기, 은은한 확대·축소와 밝기 변화.
- 위치, 크기, 지연, 지속시간, 투명도를 다르게 하되 빠른 점멸이나 과한 흔들림은 피한다. ZIP의 속도를 우선 참고하고, 자료가 없으면 약 8~20초 범위를 사용한다.
- 모바일은 대략 10~14개, 큰 화면은 18~24개 이내로 제한한다. 주요 입력 영역을 피하고 가장자리 위주로 배치한다.
- 장식 레이어는 `pointer-events: none`, `aria-hidden="true"`, `user-select: none`을 적용하고 카드보다 뒤에 둔다.
- CSS transform과 opacity 위주로 구현한다. 매 프레임 React state를 갱신하지 않는다.
- SSR에서 무작위 값 때문에 hydration 오류가 생기지 않도록 고정 seed 또는 mount 이후 생성 방식을 사용한다. 입력할 때마다 위치가 재생성되지 않게 한다.
- 움직임 끄기/켜기는 localStorage에 기억한다. 첫 방문에는 prefers-reduced-motion을 존중하고, 움직임을 끄면 배경 조명 애니메이션도 함께 멈춘다.
- 비활성 탭에서는 애니메이션을 일시 정지하고 컴포넌트 제거 시 이벤트와 타이머를 정리한다.
- 입력 중이나 전송 완료 상태에서도 화면이 흔들리거나 폼 레이아웃이 바뀌지 않게 한다.

## 7. 완료 기준과 전달물

관련 기능만 집중 검증하고 다음을 실제 결과로 보고한다.

- 이름을 비우면 익명으로 저장되고 한글·일본어·이모지·개행이 보존된다.
- 2,000줄/2,001줄 경계, 바이트 상한, 공백뿐인 내용에 대해 클라이언트와 서버 검증이 일치한다.
- 제출 직후 새로고침·다른 탭에서도 제한되고, 서버 시각 기준 48시간 전/후 경계가 정확하다. 테스트에서 시각을 제어하고 실제로 48시간 기다리지 않는다.
- 동일 식별자의 동시 요청과 응답 유실 후 재시도에서 한 건만 저장된다. 실패하면 작성 내용이 유지되고 제한이 시작되지 않는다.
- localStorage 값 조작만으로 서버 제한을 해제할 수 없다. anon 키 직접 요청으로 편지 조회·삽입·검수 상태 변경이 불가능하다.
- XSS 입력이 실행되지 않고 API 응답·로그에 원문이나 비밀키가 불필요하게 포함되지 않는다.
- 360px 모바일, 태블릿, 데스크톱에서 가로 넘침과 버튼 가림이 없으며 모션 감소 설정이 작동한다.
- 기존 프로젝트의 lint/typecheck/build를 해당하는 범위에서 실행한다. 실행 불가능한 검증과 실제 완료한 검증을 구분한다.

최종 전달물:

1. 팬 작성 페이지, 애니메이션 컴포넌트, API 및 DB 처리 코드.
2. Supabase migration SQL, 필요한 환경변수 이름만 포함한 예시.
3. `docs/fan-letters.md`: 로컬 실행, DB 적용, 검증 방법, 48시간 제한 방식과 한계, 이후 관리자·모카 화면 연결 지점. 비개발자도 따라갈 수 있게 짧고 쉽게 작성한다.
4. 변경 파일, 검증 결과, 남은 설정, 마이그레이션 적용 여부를 간단히 요약한다.

기존 파일을 먼저 확인하고 최소 변경으로 완성하라. 자료나 원격 권한이 일부 부족해도 구현 가능한 작업을 끝내고, 남은 수동 설정만 정확하게 안내하라.
